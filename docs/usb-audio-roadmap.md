# clock_codex USB 音频路线图

## 目的

本文记录将 `clock_codex` 逐步演进为一个基于 `ESP32-S3` 的 USB 连接电脑音箱时，当前规划中的方向。

它的存在是为了避免未来会话不得不从聊天记录里重建整个计划。

## 目标方向

期望的最终状态是：

- 开发板通过 `OTG` USB 端口连接到电脑
- 电脑把开发板识别为 `USB Audio Device`
- 开发板从电脑接收音频
- 开发板通过现有 `I2S` 输出路径将音频转发到 `MAX98357A`
- 当前 `TTL` 端口在开发期间仍保留用于刷机与串口日志

当前认知：

- `OTG` 应同时承担 USB 音频与 USB 供电
- `TTL` 应保留用于日志与 bring-up
- `ESP32-S3` 原生 USB 使用 `GPIO19/GPIO20`
- 当前 SD 接线已经使用了 `GPIO19`，因此从长期看，SD 与 USB 音频的硬件方案不能默认继续沿用当前 SD 映射

## 指导规则

不要从当前 `SD Audio` 实现直接跳到一个与 USB 强耦合的专用播放路径。

应先拆分：

- 音频源选择
- 音频数据生产或流式输入
- 音频输出传输

现有 `audio_output` 模块应继续作为 `I2S` 播放输出的唯一拥有者。

## 计划阶段

## 阶段 1：解耦音频源与音频输出

目标：

- 保持当前应用行为不变
- 让播放协调器不再直接持有 `WAV` 与 `MP3` 的具体细节

计划：

- 重构 `app_music_service`，使其负责协调播放，而不是持有所有源特定细节
- 引入一个面向音源的抽象层，用于打开、读取和关闭音频流
- 保持 `audio_output` 只负责 `I2S` 发送

预期的临时音源：

- 音调源
- SD WAV 音源
- SD MP3 音源

为什么这一阶段必须先做：

- 它能在 USB 工作开始前降低风险
- 它能建立一个稳定的插入点，供未来 USB 音源接入
- 它能保住 services 与 drivers 之间的架构边界

## 阶段 2：把 Tone 与 SD 作为回归音源

目标：

- 证明重构没有破坏已知良好的播放路径

必做检查：

- 音调播放仍能干净地启动与停止
- 已知良好的 WAV 播放仍然正常
- 已知良好的 MP3 播放仍然正常
- 音源切换不会破坏输出路径
- 播放停止、重启与文件切换仍然稳定

当前说明：

- 在这一阶段中，SD 被保留为测试与回归工具，而不是长期主产品方向

## 阶段 3：降低 SD 的主线功能地位

目标：

- 保留源码足够长时间，以支持回归测试
- 不再把 SD 音频视为长期产品优先方向

计划：

- 将音调保留为永久性的最小回归音源
- 在 USB 音频 bring-up 期间暂时保留 SD 音频
- 一旦 USB 音频稳定，就按需要移除或隐藏与 SD 强相关的 UI 与工作流

重要硬件说明：

- 由于 `GPIO19` 当前被 SD `MISO` 使用，现有 SD 接线与原生 USB 使用存在冲突
- 不要假定当前 SD 引脚映射能一直保留到 USB 音箱里程碑

## 阶段 4：构建最小 USB 音频闭环

目标：

- 让电脑能够向开发板发送音频，且开发板能把它播放出来

最小可行范围：

- 只做播放
- 不做麦克风路径
- 不做语音路径
- 先只支持一种稳定的 PCM 格式
- 将接收到的 USB 音频写入服务层自有缓冲区
- 通过现有 `audio_output` 模块消费这份缓冲区

建议的首个目标：

- 立体声
- 16-bit PCM
- 先固定一个最利于 bring-up 的采样率

当前实现说明：

- 仓库现在已经具备服务层自有的 USB PCM 环形缓冲区骨架
- 播放协调器现在已经能把 `USB Audio` 视为一种音源后端，而无需改动 `audio_output`
- 该后端的启动行为现在会等到缓存帧达到最小阈值后再启动输出
- TinyUSB 设备初始化、首版音箱描述符与数据包摄取逻辑现在已在专用 USB 音频服务中实现
- 这条路径已经在真实 Windows 硬件上完成首次播放验证
- 一个关键的 bring-up 修复是：按有界的单包大小分块排空 TinyUSB 数据，而不是试图把跨越数毫秒的突发音频塞进单个 USB 包大小的栈缓冲区

## 阶段 5：稳定 USB 音频路径

目标：

- 从“第一次出声”推进到“可靠播放”

当前状态：

- 项目当前已经进入这一阶段
- Windows 枚举与首次可闻播放已成功
- 剩余工作主要集中在稳定性、清理与 UX 打磨

可能的工作项：

- 环形缓冲区调优
- 播放启动阈值
- underrun 处理
- overflow 处理
- 静音填充策略
- 断开与重连行为
- 面向 UI 的源状态与缓冲区健康诊断
- 在主机侧验证描述符与 alternate-setting 行为

## 推荐的服务结构

随着代码演进，优先采用以下职责拆分：

- `audio_output`
  - `I2S` 播放拥有者
- 各类音源实现
  - tone
  - SD WAV
  - SD MP3
  - 未来的 USB 流
- `app_services` 中的播放协调器
  - 持有状态
  - 选择当前激活音源
  - 驱动“缓冲区 -> 输出”流程
- `app_ui`
  - 反映状态
  - 发送播放命令
  - 不得直接访问 USB、SD 或 `I2S` 内部细节

## 短期决策

在真正全面展开 USB 实现之前：

1. 完成音源 / 输出解耦
2. 验证 Tone 与 SD 回归播放
3. 然后再开始 USB 音频最小闭环里程碑

除非后续新的里程碑文档替代本文，否则这就是当前预期方向。
